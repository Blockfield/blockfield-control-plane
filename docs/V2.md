# Control-plane v2 core (migration step 2)

This is a separately launched implementation, with no production migration or
consumer cutover. The image's default U1 command remains unchanged. Run v2 using
`python -m cpv2` only after the independently approved database/bootstrap setup.
The site, proxy, Game and Workshop still require their later migration steps.

## Ownership and bootstrap

Use a dedicated control database, separate from statistics. `CP_DATABASE_URL`
is the sole new runtime secret: a least-privilege login inheriting `cp_runtime`,
with no database/schema ownership, superuser, role-creation or database-creation
rights. The API refuses powerful DSNs and an unbootstrapped database. Database
roles are provisioned by the owner; the API never runs migrations. `CP_PORT`
retains its existing meaning. No site owner UUID or U1 bootstrap env is read.

The operator uses a **different** database-owner credential in a private regular
file; it must never be installed into the runtime environment, site or CI.

```
python -m cpv2.admin --database-file /run/secrets/cp-migration migrate --database <control-db-name>
python -m cpv2.admin --database-file /run/secrets/cp-migration bootstrap \
  --account <internal-UUID> --name <owner-name> --credential-file /run/secrets/owner-registration
```

Bootstrap accepts an independently verified WebAuthn registration record:
`id` (base64url credential ID), `publicKey` (base64url COSE public key), `rpId`
and HTTPS `origin`. Perform registration with the owner's authenticator outside
the site, on the future central owner origin. This core does not provide a
registration UI or recover a credential from Drasl. The offline operator verifies
the registration ceremony and origin; the bootstrap file is a trust root, not an
untrusted browser attestation. Repeated bootstrap refuses; recovery is a separately
reviewed offline migration, not an API route or automatic empty-DB reseed.

Migration creates protected owner membership/key tables and code-owned client and
setting definitions. Runtime can select their public metadata, but cannot write
it. It cannot update/delete audit, settings revisions, outbox, receipts or event
history. Runtime credentials never go to site/bot/agents. Database/root/deployment
authority remains inside the owner trust boundary. Backup/PITR, ingress TLS and
separate owner origin are prerequisites for a later production switch, not
resources provisioned by this PR.

`admin provision --spec-file FILE --token-file NEW_FILE` is an offline operator
seed for accounts, scoped grants, bounded sessions, registered clients and agents.
It emits a random bearer only to a new mode-0600 file, stores only its SHA256
verifier, and records recovery provenance. See `cpv2/admin.py:provision` for the
explicit spec fields. Internal accounts are never inferred from a nickname or
recycled Drasl UUID. `account_identities` reserves issuer/user/player bindings;
verified Drasl login/linking and its UI belong to step 3. No password-login
endpoint or service-supplied `actAs` exists in this core.

## API contract

`GET /openapi.json` (also `/v1/openapi.json`) exposes generated input schemas.
Every v2 request uses an audience-bound bearer. Session permissions intersect
current account grants, credential ceiling, registered client ceiling and exact
environment/backend/resource. Roles are fixed in code. Owner membership alone is
insufficient on a non-human client or delegation. Ordinary grants never accept
owner; admins cannot edit themselves, peers, owners or admin grants. Security
changes increment authorization epoch, revoke credentials and wake streams.

- `GET /v2/me`, `GET /v2/settings/catalog`, `GET/PATCH /v2/settings/{namespace}/{target}`.
- `POST .../validate`: normalized preview, no revision or delivery.
- `POST .../rollback`: new CAS revision under current validation and field policy.
- `POST /v2/staff/grants`: add/revoke lower grants; admin changes require owner approval.
- `POST /v2/accounts/{id}/test-status`: owner-approved classification, permanent privacy flag.
- `POST /v2/actions/moderation.kick|moderation.ban`: bounded, typed, generation-bound commands.
- `GET /v2/operations/{id}`: accepted separately from received/validated/applied/effective.
- `GET /v2/events?after=N`: authenticated, resource-scoped own-operation SSE history.
- `POST /v2/delegations`: bounded lower-scope human session only, never owner authority.
- `DELETE /v2/sessions/current`: revoke current credential and descendants.
- `GET /v2/audit`: redacted own operations for admin, full allowed audit for owner.

Settings registry holds `gate`, `gameplay` and the site settings
namespaces below. Unknown keys and types are rejected, including Boolean/float CAS
revisions. Settings PATCH follows RFC 7396 JSON Merge Patch: a `null` value
deletes that key (recursively in nested objects) before validation; absent keys
are untouched and arrays are replaced wholesale. Deletion is validated like any
other change, so a merged result that breaks an invariant is rejected with 422
while dict namespaces may become empty. Nullable scalars (`rooms.*`,
`deathmatch.minPlayers`) reset to their `None` default when deleted. The only
stored-null exception is `kits.fixedModeKits.<mode>` ("kit id or null"): `null`
clears the fixed kit but keeps the explicit entry. Settings reads explicitly distinguish `initialized=false` defaults from
initialized revision-zero imports and subsequent v2 revisions. Full normalized
object validation enforces AI budget against its hard
limit. The `ai.hardLimit` child is protected even in a parent patch or rollback.
A protected subtree (for example `ai-limits` `sessions.<uuid>`) matches by prefix,
so nested money changes cannot slip past the owner check. A repeated delegation
key returns the existing operation/credential IDs without
re-emitting the one-time token. Observer/audit sequence allocation happens after business locks, under a short
transaction lock held through commit, so cursors cannot skip a late commit.
Business mutations remain concurrent; history rows are flushed atomically at
transaction completion. Slow mutations do not hold the history lock while working.

|---|---|---|---|
| `rooms` | settings.json `rooms` | `settings.gameplay.write` | — |
| `deathmatch` | settings.json `deathmatch` | `settings.gameplay.write` | — |
| `classLocks` | settings.json `classLocks` + `classCosts` | `settings.gameplay.write` | — |

No DSNs, URLs, shell/console commands, credentials, policy definitions or arbitrary
files are accepted as settings. More catalog namespaces require reviewed code.

An owner requests `POST /v2/owner/challenges` with method/path/body, then submits a
WebAuthn authentication response in `X-CP-Owner-Assertion` as JSON containing
`challengeId` and `credential`. The assertion requires authenticator user
verification and binds the nonce to actor/session, audience, full canonical action,
60-second expiry and one-time use. Invalid/replayed assertions cannot authorize
another operation; an already accepted idempotent operation may be retrieved.
Unattended clients cannot mint owner challenges. There is no cookie auth or
permissive CORS, so site cookies and caller-supplied actors are not authority.

Every mutation commits a bounded pending audit attempt before parsing/validation
and commits accepted changes, audit and outbox together. Invalid/denied attempts
are append-only evidence. A transaction/audit failure prevents acceptance; pending
records remain for reconciliation. Payload errors omit values and exception text.
Audit rows carry environment/backend/resource independently of the operation FK,
so scoped reads keep pending/denied evidence without leaking other scopes. Owner
role never bypasses requested scope filters. Unknown/global bootstrap and
unauthenticated attempts require a credential and request covering `*` in all
three dimensions. There is no destructive count retention. Audit export/anchoring and operational
break-glass ingestion remain rollout work; same-DB append-only controls do not
claim protection against database owners.

## Private delivery

An offline-provisioned service credential is bound to exactly one consumer,
environment/backend/resource, generation, epoch and capability list. It cannot
issue sessions, grants or owner credentials.

1. `GET /v2/agents/{id}/snapshot` obtains current target-scoped settings plus
   epoch, generation and durable received cursor over authenticated TLS.
2. `GET /v2/agents/{id}/events?epoch=UUID&cursor=N` opens SSE. `Last-Event-ID`
   is `epoch:sequence`. Epoch mismatch or an unacknowledged forward cursor returns
   `409 snapshot_required`. Snapshot never executes actions or advances ACKs.
3. Frames contain schema, epoch, per-consumer sequence, operation/audience,
   generation, revision, payload hash, auth epoch and expiry. Consumers persist
   receipt/dedup before applying at their safe runtime boundary.
4. `POST /v2/agents/{id}/acks` sends that envelope identity, state,
   timezone-qualified `actualAt` and a bounded result code. State order is
   received → validated → applied → effective; rejected/unknown are terminal.
   Exact duplicate receipts succeed; changed duplicates or sequence gaps fail.
   The reconnect cursor advances only across contiguous persisted receipts.
   Authorization/deadline/head checks gate received/validated work; later
   applied/effective receipts record authenticated executor facts even after the
   issuer is revoked, a deadline passes or a newer desired revision exists.

The per-consumer sequence is allocated under a row lock in the same transaction
as its outbox row, so concurrent commits cannot create out-of-order publication.
PostgreSQL LISTEN/NOTIFY only wakes the async dispatcher; durable rows remain
source of truth on disconnect/restart/lost notification. A 10-second bounded
recovery/authorization check supplements the wake path. Streams buffer at most
64 rows, with 2 connections per consumer and 64 globally. A lagging consumer
blocks new transient actions beyond 128 outstanding frames. Configuration and
short-lived actions share the bounded control stream; telemetry is outside it.

Queued operations recheck credential/account epoch and role scopes. Expired,
revoked, superseded or terminal work is streamed as a non-executable cursor frame,
never as an executable command. Socket delivery does not imply received/applied.
ACK records include authenticated service attribution and hashes; multiple targets
retain independent receipts and cannot report effective until all confirm.
Unknown effects are terminal and require operator reconciliation, never blind
retry. Generation replacement is an offline reviewed registration change; it
requires explicit new epoch and reconciliation of old operations.

## SQLite migration and compatibility

Fence the U1 writer, checkpoint SQLite and verify a backup **before** importing.
Run `admin import-u1 --sqlite BACKUP` against an unused staging control store.
Import retains gate revision/history/audit/token metadata with a source-file
SHA256 and per-table count/hash manifest. Historical actors remain unverified
legacy records, inaccessible to runtime. Only unexpired, unrevoked gate-read
verifiers retain read compatibility. Old shared write tokens gain no v2 authority.
Repeated identical import verifies the manifest; a changed source cannot overwrite
a populated staging store. No notifications or executor effects occur during import.

`GET /v1/gate` and gate-consumer snapshots include the initialized imported state
even at revision zero, or the latest v2 gate revision;
`POST /v1/gate` has no v2 handler. Without an imported/explicit desired state,
v1 reads fail closed. Gate revisions continue monotonically after import. The
legacy `api.py` and default container command remain available during review;
production cutover must fence it so there is exactly one writer.

## Verification

`uv run --frozen python scripts/check_v2.py` is the pinned gate, on an owned Boat
VM (`BLOCKFIELD_BOAT_VM=1`) or CI. It checks formatting/lint and the full legacy
and v2 suites. The locked `pgserver` wheel bundles PostgreSQL for disposable
Unix-socket databases under project `.cache`; no global package installation,
Docker daemon, shared DB or production credentials are needed. Fixtures always
close their pools/listener and stop the owned backend. The CI gate uses the same
hash-pinned dependency export. Real consumer/game/latency and PostgreSQL 18/PITR
acceptance remain required before production migration; unit ACKs are fake
executor receipts, not proof of applied gameplay.
