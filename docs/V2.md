# Control-plane v2 core

This is the production implementation. The image default runs v2 as
`python -m cpv2` against the independently approved database/bootstrap setup.

## Ownership and bootstrap

Use a dedicated control database, separate from statistics. `CP_DATABASE_URL`
is the sole new runtime secret: a least-privilege login inheriting `cp_runtime`,
with no database/schema ownership, superuser, role-creation or database-creation
rights. The API refuses powerful DSNs and an unbootstrapped database. Database
roles are provisioned by the owner; the API never runs migrations. `CP_PORT`
retains its existing meaning. No site owner UUID is read.

The operator uses a **different** database-owner credential in a private regular
file; it must never be installed into the runtime environment, site or CI.

```
python -m cpv2.admin --database-file /run/secrets/cp-migration migrate --database <control-db-name>
python -m cpv2.admin --database-file /run/secrets/cp-migration bootstrap \
  --account <internal-UUID> --name <owner-name> --credential-file /run/secrets/owner-registration
```

Bootstrap accepts an independently verified WebAuthn registration record:
`id` (base64url credential ID), `publicKey` (base64url COSE public key), `rpId`
and HTTPS `origin`. Perform registration with the owner's authenticator outside
the site, on the future central owner origin. The static helper
`scripts/cp-bootstrap.html` (no server route, no build) runs that ceremony on
the owner origin with the owner's authenticator and prints the
`--credential-file` JSON; save its output into an owned mode-0600 file. The core
still recovers no credential from Drasl. The offline operator verifies
the registration ceremony and origin; the bootstrap file is a trust root, not an
untrusted browser attestation. Repeated bootstrap refuses; recovery is a separately
reviewed offline migration, not an API route or automatic empty-DB reseed. The second founder joins the same way via `admin enroll-owner` (same checks, same audit shape under `owner.enroll`): the owner list then holds exactly both founders, and no further owner can be enrolled.

Migration creates protected owner membership/key tables and code-owned client and
setting definitions. Runtime can select their public metadata, but cannot write
it. It cannot update/delete audit, settings revisions, outbox, receipts or event
history. Runtime credentials never go to site/bot/agents. Database/root/deployment
authority remains inside the owner trust boundary. Backup/PITR, ingress TLS and
separate owner origin are prerequisites for a later production switch, not
resources provisioned by this PR.

`admin provision --spec-file FILE --token-file NEW_FILE` is an offline operator
seed for accounts, scoped grants, bounded sessions, registered clients and agents.
It emits a random bearer only to a new mode-0600 file, stores only its SHA256
verifier, and records recovery provenance. See `cpv2/admin.py:provision` for the
explicit spec fields. Internal accounts are never inferred from a nickname or
recycled Drasl UUID. `account_identities` reserves issuer/user/player bindings;
verified Drasl login/linking and its UI belong to step 3. No password-login
endpoint exists in this core. The service-supplied actors are
`GrantChange.actorAccountId`, accepted solely from a service credential
provisioned with the staff scopes, and `SettingsChange`/`Rollback`
`actorAccountId`, accepted solely from a service credential provisioned with
the site settings scopes (`settings.read`, `settings.gameplay.write` on
`prod/game/*`); both name the acting account and are evaluated under the same
peer and owner step-up rules as a direct call
(see the site staff service below). Moderation actions (`Action` and
`ModerationAction`) carry the same `actorAccountId` field with the same
rules, so the site moderation token is a service credential with a
`moderation.*` ceiling plus a per-request actor assertion.

Service credentials (account-less) expire after at most 30 days and are
re-issued monthly; human session credentials after at most 24h. On success
`provision` prints one JSON line with `credentialId` and `fingerprint` (the
verifier prefix, never the token). `admin revoke --credential-id` revokes a
credential offline (idempotent; unknown ids are refused) and records
`credentials.revoke`.

## API contract

`GET /openapi.json` (also `/v1/openapi.json`) exposes generated input schemas.
Every v2 request uses an audience-bound bearer. Session permissions intersect
current account grants, credential ceiling, registered client ceiling and exact
environment/backend/resource. Roles are fixed in code. Owner membership alone is
insufficient on a non-human client or delegation. Ordinary grants never accept
owner; admins cannot edit themselves, peers, owners or admin grants. Security
changes increment authorization epoch, revoke credentials and wake streams.

- `GET /v2/me`, `GET /v2/settings/catalog`, `GET/PATCH /v2/settings/{namespace}/{target}`.
  Game settings writes ride the same actor assertion as staff/moderation: the
  site settings token is a service credential with a `settings.read` +
  `settings.gameplay.write` ceiling on `prod/game/*`, and every write must
  send `actorAccountId` (the logged-in site admin); CP re-resolves that
  actor's account, live grants and owner membership, then applies the same
  scope rules a direct call gets. Namespaces with protected paths
  (all of `ai-limits` and `workshop-ai`) stay
  owner-only: the owner step-up needs a direct owner session, so a
  service-asserted owner fails closed. A service write without an actor is
  refused (`service_actor_required`); a direct call carrying `actorAccountId`
  is refused (`actor_forbidden`).
- `POST .../validate`: normalized preview, no revision or delivery.
- `POST .../rollback`: new CAS revision under current validation and field policy.
- `GET /v2/staff/grants?accountId=`: live grants plus the compare-and-set
  revision for one account; `staff.read` service scope only.
- `POST /v2/staff/grants`: add/revoke lower grants; admin changes require owner approval.
  Service callers must send `actorAccountId`; direct callers must not.
- `POST /v2/accounts/{id}/test-status`: owner-approved classification, permanent privacy flag.
- `POST /v2/actions/moderation.kick|moderation.ban`: bounded, typed, generation-bound commands. The site's remaining RCON writes ride the same path: `moderation.say|list|pardon|team-kick|class-lock|class-unlock|range|stop-room` (scope equals kind; `pardon` needs admin like `ban`). A service credential holding `moderation.*` must send `actorAccountId` (the logged-in site user); CP re-resolves that actor's account, live grants and owner membership, then applies the same scope rules a direct call gets. A service call without an actor is refused (`service_actor_required`); a direct call carrying `actorAccountId` is refused (`actor_forbidden`).
- `POST /v2/actions/moderation.maintenance`: `op` `status|drain|resume|interrupt` (`interrupt` needs `reason`); admin scope, site-asserted like the other moderation kinds. `POST /v2/actions/moderation.announce`: the deploy restart notice, no fields; service credentials only, never with `actorAccountId` (the text is fixed in the game).
- `POST /v2/actions/console.run` (coordination#35): `{command, consumerId, generation, target?}`, one line ≤ 1000 chars without control characters. CP classifies the line against `core.CONSOLE_READ_ONLY` (`list`, `tick query`, `bf maintenance status`, `banlist`, `whitelist list`, `spark tps|health|gc|tickmonitor`): allowlisted lines need `console.read`, anything else `console.run`. Neither scope is in a role: owners hold both; a service credential holds them only when an owner provisions it — the site console principal, which must assert an owner via `actorAccountId`, and the agent MCP tokens, which send no actor. The payload carries `command` and `readOnly`; the game re-checks `readOnly` lines against the same list. The accepted audit row keeps the command line.
- Command output (list, maintenance, console): the executor sends it as `output` (≤ 64 KiB) on the terminal ack; it is stored in the receipt's `result.output` and is not part of the receipt fingerprint. The issuing credential may always read its own `GET /v2/operations/{id}`, so service callers poll output without `operations.read`.
- `PATCH /v2/settings/gate/workshop`: the workshop controller's gate leg, reported with the service-holdable `workshop.gate` scope. That scope authorizes only this route, within the credential's provisioned environment/backend/resource; rollback and validate under it are refused, and any other service-issued settings operation stays rejected at delivery. The reporter may read the leg back with the same scope to report idempotically; nobody else needs it.
- `POST /v2/workshop/members|message|wake|cancel|release.select`: typed Workshop operations for the Workshop subscriber.

Workshop operations carry the exact typed payloads the Workshop subscriber applies (`members`, `message`, `wake`, `cancel`, `release.select`, plus the remaining inbox kinds `map`, `sessions`, `ai-key`, `mode`), plus the authorized `target` (`*` or the granted resource) in every payload so the consumer can check an operation is addressed to itself; member entries with `maps` require target `*`, since map ids are outside any scoped grant, and the `map`/`sessions`/`ai-key`/`mode` kinds always require target `*` for the same reason. The commit path reuses operations/outbox/enqueue with the required `workshop.*` scope per kind (`moderation`-style: `message`/`wake`/`cancel`/`map` need moderator or admin, `sessions` needs any staff role, `members`/`release.select`/`mode` need admin, `ai-key` needs an owner) and fans out only to consumers provisioned with the matching capability. The frame payload hash is the canonical-JSON digest the Workshop verifies. Caller attribution is bound, never caller-supplied (see API contract on audience-bound bearers and role scopes): a person session must have exactly one `drasl`-issuer account_identities row and the payload actor/grantor is derived from it, while a service principal (site/bot acting for a human over an API-only plane) may supply the actor only with the offline-provisioned `workshop.act` scope, consistent with Ownership and bootstrap (no service-supplied actAs: the act authority is provisioned offline, never self-minted) and Private delivery (service credentials stay bound to one consumer/scope set); the audit records both the service principal and the workshop actor, and consumer agent credentials must never carry `workshop.*` or `workshop.act`. Admin-role member entries require the same owner step-up as `grant_change` (challenge `POST /v2/workshop/members`), or they are denied. Workshop consumers must enforce `payload.target` (exact field) before applying and reject `members[].maps` under a scoped target; snapshot-advisory records carry no target by design. Release-record provenance is verified consumer-side against its catalog. The `ai-key` payload carries the key itself (absent `key` is rejected; explicit null removes it): unlike every other kind, key material persists in the control store's outbox row, inside the owner trust boundary — audit, operation results, snapshots and responses carry only the payload hash, never the key, and validation errors never echo it. The `sessions` kind attests and authorizes the draft-listing query; the listing itself reaches the site through the consumer's follow-up result path, so the sessions inbox reader stays until that lands.
- `GET /v2/operations/{id}`: accepted separately from received/validated/applied/effective.
- `GET /v2/events?after=N`: authenticated, resource-scoped own-operation SSE history.
- `POST /v2/delegations`: bounded lower-scope human session only, never owner authority.
- `DELETE /v2/sessions/current`: revoke current credential and descendants.
- `POST /v2/credentials/renew` (service credentials): issues a successor with the same client, scopes,
  consumer binding and lifetime (capped at 30 days) and returns its token. The old credential stays
  valid for 1 hour or until `POST /v2/credentials/renew/confirm` is called with the new token, which
  revokes it. Retrying renew with the old token returns the same successor; renew with an
  unconfirmed successor is refused (409). `GET /v2/me` carries `issuedAt`/`expiresAt` for scheduling.
- `POST /v2/site/sessions`, `GET /v2/site/sessions/{id}`, `DELETE /v2/site/sessions/{id}`, `DELETE /v2/site/users/{uuid}/sessions`: site player sessions (coordination#29). Sealed Drasl tokens live in CP, the site is a stateless client; 20 per player, 60-day idle expiry, prune on create, touch on read. `site.sessions` service scope only (unbound site credential) plus founders; never in a human role.
- `POST /v2/stats/results`: game-producer match/campaign ingest (coordination#29 U1). Stores the result, participants, class breakdown and display-name cache in one transaction with the producer's idempotency semantics: new `(server_id,event_id)` → 201 `{inserted:true,eventId}`, exact replay → 200 `{inserted:false,eventId}`, same id with different content → 409. Bodies up to 1 MiB (the producer outbox contract). `stats.ingest` service scope only, provisioned bound to the server's resource (`spec.resource` is the server UUID, never `*`), never in a human role; production posture is one credential per game server. CP stats start with the new season: no history import, no rating compute yet (reads and MMR replay the stored payloads in a later unit).
- `POST /v2/stats/diagnostics`, `GET /v2/stats/diagnostics`: game-producer health samples and freeze/error journal (coordination#29 U4). Same bytes, idempotency and retention caps as the site `POST /api/stats/diagnostics` (50k samples over 7 days, 5k events over 14 days with crash/error priority); ingest under the per-server `stats.ingest` credential, reads under `stats.read`. The site admin «Производительность» view reads the GET route when configured; the producer cuts over to the POST route directly.
- `GET /v2/audit`: redacted own operations for admin, full allowed audit for owner.

Settings registry holds `gate`, `gameplay` and the site settings
namespaces below. Unknown keys and types are rejected, including Boolean/float CAS
revisions. Settings PATCH follows RFC 7396 JSON Merge Patch: a `null` value
deletes that key (recursively in nested objects) before validation; absent keys
are untouched and arrays are replaced wholesale. Deletion is validated like any
other change, so a merged result that breaks an invariant is rejected with 422
while dict namespaces may become empty. Nullable scalars (`rooms.*`,
`deathmatch.minPlayers`) reset to their `None` default when deleted. The only
stored-null exception is `kits.fixedModeKits.<mode>` ("kit id or null"): `null`
clears the fixed kit but keeps the explicit entry. Settings reads explicitly distinguish `initialized=false` defaults from
initialized revision-zero imports and subsequent v2 revisions. Full normalized
object validation rejects unknown fields, mistyped values and range
violations.
A protected subtree (for example `ai-limits` `sessions.<uuid>`) matches by prefix,
so nested money changes cannot slip past the owner check. A repeated delegation
key returns the existing operation/credential IDs without
re-emitting the one-time token. Observer/audit sequence allocation happens after business locks, under a short
transaction lock held through commit, so cursors cannot skip a late commit.
Business mutations remain concurrent; history rows are flushed atomically at
transaction completion. Slow mutations do not hold the history lock while working.

|---|---|---|---|
| `rooms` | settings.json `rooms` | `settings.gameplay.write` | — |
| `deathmatch` | settings.json `deathmatch` | `settings.gameplay.write` | — |
| `classLocks` | settings.json `classLocks` + `classCosts` | `settings.gameplay.write` | — |

No DSNs, URLs, shell/console commands, credentials, policy definitions or arbitrary
files are accepted as settings. More catalog namespaces require reviewed code.

An owner requests `POST /v2/owner/challenges` with method/path/body, then submits a
WebAuthn authentication response in `X-CP-Owner-Assertion` as JSON containing
`challengeId` and `credential`. The assertion requires authenticator user
verification and binds the nonce to actor/session, audience, full canonical action,
60-second expiry and one-time use. Invalid/replayed assertions cannot authorize
another operation; an already accepted idempotent operation may be retrieved.
Unattended clients cannot mint owner challenges. There is no cookie auth or
permissive CORS, so site cookies are not authority, and human callers cannot
assert an actor.

Site staff service. The site (API-only, no human CP steps) calls CP with one
offline-provisioned service principal, e.g. client id `site` with ceiling
`["staff.read", "staff.lower.manage", "staff.admin.manage"]` on
`prod/game/*`; no other credential holds these ceilings, and `staff.read`
exists in no human role or owner scope. `GET /v2/staff/grants?accountId=`
returns that account's live grants plus `expectedRevision` (its authorization
epoch) for compare-and-set writes. `POST /v2/staff/grants` from a service
credential requires `actorAccountId`: the logged-in site user the change is
attributed to. CP re-resolves that actor's account, live grants and owner
membership, then applies the same scope, self-edit, peer and owner step-up
rules a direct call gets; the operation, the role-grant row and the audit
entries carry the actor, while the service credential and client stay on the
record. A service call without an actor is refused
(`service_actor_required`); a direct call carrying `actorAccountId` is
refused (`actor_forbidden`). An owner asserted through the service still
needs owner step-up, which only a direct owner session can satisfy, so admin
changes by an owner-actor fail closed until per-user bearer linking lands.
The site sends its service bearer plus, per write, `accountId`,
`expectedRevision` from the roster read, `role`/`resource`/`revoke`, a fresh
`idempotencyKey`, and `actorAccountId` of the logged-in user.

Every mutation commits a bounded pending audit attempt before parsing/validation
and commits accepted changes, audit and outbox together. Invalid/denied attempts
are append-only evidence. A transaction/audit failure prevents acceptance; pending
records remain for reconciliation. Payload errors omit values and exception text.
Audit rows carry environment/backend/resource independently of the operation FK,
so scoped reads keep pending/denied evidence without leaking other scopes. Owner
role never bypasses requested scope filters. Unknown/global bootstrap and
unauthenticated attempts require a credential and request covering `*` in all
three dimensions. There is no destructive count retention. Audit export/anchoring and operational
break-glass ingestion remain rollout work; same-DB append-only controls do not
claim protection against database owners.

## Private delivery

An offline-provisioned service credential is bound to exactly one consumer,
environment/backend/resource, generation, epoch and capability list. It cannot
issue sessions, delegation credentials or owner credentials, and a consumer
agent credential carries no staff scopes (those belong to the site principal
above).

1. `GET /v2/agents/{id}/snapshot` obtains current target-scoped settings plus
   epoch, generation and durable received cursor over authenticated TLS.
2. `GET /v2/agents/{id}/events?epoch=UUID&cursor=N` opens SSE. `Last-Event-ID`
   is `epoch:sequence`. Epoch mismatch or an unacknowledged forward cursor returns
   `409 snapshot_required`. Snapshot never executes actions or advances ACKs.
3. Frames contain schema, epoch, per-consumer sequence, operation/audience,
   generation, revision, payload hash, auth epoch and expiry. Consumers persist
   receipt/dedup before applying at their safe runtime boundary.
4. `POST /v2/agents/{id}/acks` sends that envelope identity, state,
   timezone-qualified `actualAt` and a bounded result code. State order is
   received → validated → applied → effective; rejected/unknown are terminal.
   Exact duplicate receipts succeed; changed duplicates or sequence gaps fail.
   The reconnect cursor advances only across contiguous persisted receipts.
   Authorization/deadline/head checks gate received/validated work; later
   applied/effective receipts record authenticated executor facts even after the
   issuer is revoked, a deadline passes or a newer desired revision exists.

The per-consumer sequence is allocated under a row lock in the same transaction
as its outbox row, so concurrent commits cannot create out-of-order publication.
PostgreSQL LISTEN/NOTIFY only wakes the async dispatcher; durable rows remain
source of truth on disconnect/restart/lost notification. A 10-second bounded
recovery/authorization check supplements the wake path. Streams buffer at most
64 rows, with 2 connections per consumer and 64 globally. A lagging consumer
blocks new transient actions beyond 128 outstanding frames. Configuration and
short-lived actions share the bounded control stream; telemetry is outside it.

Queued operations recheck credential/account epoch and role scopes. Expired,
revoked, superseded or terminal work is streamed as a non-executable cursor frame,
never as an executable command. Socket delivery does not imply received/applied.
ACK records include authenticated service attribution and hashes; multiple targets
retain independent receipts and cannot report effective until all confirm.
Unknown effects are terminal and require operator reconciliation, never blind
retry. Generation replacement is an offline reviewed registration change; it
requires explicit new epoch and reconciliation of old operations.

## SQLite migration and compatibility

Fence the U1 writer, checkpoint SQLite and verify a backup **before** importing.
Run `admin import-u1 --sqlite BACKUP` against an unused staging control store.
Import retains gate revision/history/audit/token metadata with a source-file
SHA256 and per-table count/hash manifest. Historical actors remain unverified
legacy records, inaccessible to runtime. Only unexpired, unrevoked gate-read
verifiers retain read compatibility. Old shared write tokens gain no v2 authority.
Repeated identical import verifies the manifest; a changed source cannot overwrite
a populated staging store. No notifications or executor effects occur during import.

`GET /v1/gate` and gate-consumer snapshots include the initialized imported state
even at revision zero, or the latest v2 gate revision;
`POST /v1/gate` has no v2 handler. Without an imported/explicit desired state,
v1 reads fail closed. Gate revisions continue monotonically after import.

## Verification

`uv run --frozen python scripts/check_v2.py` is the pinned gate, on an owned Boat
VM (`BLOCKFIELD_BOAT_VM=1`) or CI. It checks formatting/lint and the v2 suite. The locked `pgserver` wheel bundles PostgreSQL for disposable
Unix-socket databases under project `.cache`; no global package installation,
Docker daemon, shared DB or production credentials are needed. Fixtures always
close their pools/listener and stop the owned backend. The CI gate uses the same
hash-pinned dependency export. Real consumer/game/latency and PostgreSQL 18/PITR
acceptance remain required before production migration; unit ACKs are fake
executor receipts, not proof of applied gameplay.
